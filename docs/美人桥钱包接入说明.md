# 美人桥钱包一期接入说明

## 本期范围

- USDT充值、余额、钱包余额上分、充值订单与钱包流水；充值根据通道商成功回调自动入账，后台保留详情及待收款取消，不提供手动确认入账。
- **充值不收手续费，实际收到多少USDT就入账多少。** 不新增充值费配置，不影响其他业务费率。
- TRX充值、USDT兑换TRX、汇率配置及能量租赁延期；不改写已完成历史账本。

## 复用现有收款链路

1. 创建订单复用现有美人桥地址获取与分配代码，保存本单地址、网络及分配标识。地址文字、复制和二维码保持一致；刷新或重开不重新分配。
2. 接收通道商回调，复用现有回调校验、订单与币种／网络核对、交易去重和通知重试。未收到有效成功回调时保持待收款，不加余额；不另建钱包查链监听服务。
3. 校验成功回调后，按实际收款全额增加商户USDT余额，同次保存成功订单与一笔入账流水。创建订单不改余额、不换算CNY。
4. 状态、余额、流水同一事务完成；重复回调只记账一次。少付／多付／分次到账、地址有效期及取消后到账的完成条件沿用已确认的通道规则。

## 后台操作与权限

- 待收款订单仅提供详情和取消；成功／取消后仅详情。取消须填写原因，保存操作人和时间，不产生资金流水；失败保持原状态和余额。
- 不提供人工入账按钮、弹窗或人工确认接口；充值入账由服务端验证后的通道商回调触发。
- 通道回调与取消竞争同一订单终态；取消后收到真实付款回调按现有异常规则处理并保留记录，不能直接丢弃。
- 商户仅查询自己，后台限定美人桥业务；取消与回调分别校验操作权限或可信回调来源。服务端只接受本期USDT操作。

## Demo与真实服务的边界

- 页面源：`src/pages/美人桥商户钱包/美人桥商户钱包-demo.html`。`createTopup`创建零费USDT单，`collectionInfo`展示本单收款信息，`receiveTopup`模拟通道商成功回调入账。
- 折叠的“演示操作”仅模拟通道回调，不是运营人工入账入口；没有接入真实通道、转账或服务端事务。
- 旧待收款演示单在成功回调时全额入账；已完成历史账本和只读处理记录不重写。生产旧单迁移如存在须另行确认。
- 验收覆盖100USDT入100、地址三者一致、无人工入账路径、无有效回调不入账、重复回调不加款、回调与取消竞争及权限拦截。


## 钱包余额上分复用合同

- 复用现有美人桥业务订单、当前商户绑定、美人桥号／归属／代理、汇率费率及机器人MQ链路；只将本笔USDT收款来源改为钱包余额，不分配充值地址、不再等待链上付款。订单关联钱包扣款与退款流水，不能另建机器人处理系统。
- 后端静态快照依据：system模块的OrderPreDto.MerchantAmountItem、BridgeOrderServiceImpl.preOrder / autoHandler / sendAutoHandlerMessage。原USDT输入最多2位小数，按USDT×(基础汇率+浮动汇率)×(1+商户费率/10000)计算CNY，在整数元边界八舍九入。真实接入先核对线上版本；Demo不读取生产行情或发送MQ。
- 本地弹窗读取原Demo共享USDT/CNY配置和当前商户业务资料，默认值为演示。确认时重新核对快照；金额／商户绑定／规则变化时禁止按过期预览扣款。
- 钱包扣款、业务单及唯一扣款流水需同一事务；派送及重试沿用原链路，不能因MQ重投重复扣USDT。状态和金额由服务端校验，客户端金额或商户参数不可信。
- 机器人明确返回失败时，自动把本单扣除的USDT原额退回钱包，不需要后台核实或确认；结果不明／超时先保留扣款，等待最终结果。退款与订单终态、退款流水同事务提交，成功／退款竞争同一终态。退款后禁止再派送；迟到成功记录异常，不自动改写终态。
- Demo的creditOrders仅保存上分业务单展示快照；本地“机器人结果”折叠控件模拟成功／失败／未知回执，失败自动退款，不代表真实派送、服务端事务、审计或并发已接入。原订单管理／统计与真实共享业务单的联调由开发按既有接口完成。


## 付款来源与钱包流水边界

商户端钱包记录和后台钱包管理均提供上分订单页签，支持订单号、状态查询、重置、分页和详情；后台支持商户筛选，商户仅查自己。上分业务单继续复用原订单流程。只有明确以钱包余额付款且存在匹配商户、业务单、USDT数量的扣款流水，才属于钱包上分；上分订单统一展示钱包余额上分与原USDT转U直接上分，使用可信付款来源区分；转U直接上分不触发钱包扣款或退款。处理结果变动不新增账变，实际退款才新增一笔正向流水。失败回执只对存在匹配钱包扣款的本单自动原额退回，不能对无钱包扣款的机器人单退钱；无后台退款确认入口。

本地模型新增来源标记和匹配扣款流水校验；旧本轮模拟单仅在有真实匹配扣款流水时补标记，不迁移原机器人单或改写余额。正式服务端依据可信订单资金来源、扣款关联与唯一流水验证，不能信任客户端标记。


## 两种上分方式的查询边界

- 两端上分列表统一展示钱包余额上分和转U直接上分，支持方式筛选及详情；USDT数量保留业务订单记录，不能把转U数量展示成钱包扣款。
- 正式接入复用现有USDT业务订单，按可信商户ID和付款来源查询；钱包方式核对本单扣款，转U方式沿用原通道收款和业务状态。原机器人业务失败不能调用钱包自动退款。
- 原Demo业务页面仅有各自内存订单数组，没有共享订单服务。本地`directCreditOrders`为只读演示快照，用于展示转U的成功／失败／待收款等状态；缺该字段时仅补演示快照，原余额与账本不变，不代表已完成原订单联调。不得按商户名称猜测跨页归属。
- 生产应在同一业务订单来源字段上区分两种方式，不新增一套原业务资金账本；转U失败的后续处理复用原流程，本需求不指定新退款规则。
